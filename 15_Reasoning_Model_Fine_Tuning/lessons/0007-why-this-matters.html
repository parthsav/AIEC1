Lesson 0007 · Why This Matters

From Math Homework to Any Checkable Task

Lessons 0003–0006 explained the mechanism — reward, group sampling, the KL leash, watching reward climb. This lesson steps back: what is all of that actually for, and what can you build once you understand it?

Analogy first (a callback to Lesson 3) Some skills you teach by showing steps — a recipe you follow exactly. Other skills you can only teach by tasting the result and saying "better" or "worse" — you couldn't write down the perfect rule if you tried, but you can always score an attempt. Math reasoning is in that second bucket: nobody wants to hand-write a million correct reasoning traces, but checking a final number is nearly free. That gap — checking is easy, demonstrating is hard — is exactly when this whole recipe earns its keep.

The one-sentence goal of everything you just learned

Take a model that can already attempt a task, write a function that scores an attempt (even roughly), and use GRPO to make it specifically better at that task — without ever needing a big labeled dataset of "how to do it right."

Illustration — the same recipe, two different tasks

The GRPO recipe itself never changes. What changes per project is just two things: which base model you start from, and how you write the reward function.

The elegant fix: don't compare to a written-down answer — compare to the sound

GSM8K never needed a full reasoning trace, just a checkable final answer. Your guitar task doesn't need a human-labeled tab either — it needs something checkable. The original audio clip already is the answer key.

Illustration — checking a guess against reality, not against a label

This reward could be stacked, exactly like Lesson 5's five functions: a big "does it sound right" reward, plus a small "is it even playable" format reward (real fret numbers, real strings, no impossible stretches).

Being honest about the hard part GRPO doesn't grant a model a new sense. Llama-3.2 could already do basic math before GRPO sharpened it — GRPO didn't create math ability from zero. For guitar tabs, you'd need to start from a model that can already listen to audio and guess pitches at all (real tools exist — e.g. Spotify's Basic Pitch, an open-source audio-to-note model). GRPO is the last-mile sharpening step on top of an existing capability, not a way to conjure a whole new one from nothing.
A more approachable first version Skip raw audio entirely for a first attempt. Start from an existing pitch-detector's rough (already decent) output — a sequence of notes with some mistakes — and train a text model to clean that up into proper tab notation, checked against a small set of known-correct examples or graded by music-theory playability rules. That's a symbolic, text-in-text-out problem — much closer to GSM8K, and a far more realistic starting project than raw audio-in, tab-out.

One more example, to prove this isn't just for math or hypotheticals

The DeepSeek-R1 paper — the same one behind this whole notebook — didn't only use verifiable rewards for math. It also trained on coding, where the reward is simply: does the code compile and pass the test cases? Same recipe, same loop, completely different domain. That's the real generality of what you've just learned.

Primary source DeepSeek-R1 — Section 2 describes exactly this: rule-based rewards for both math (answer correctness) and code (compiler/test-case feedback), no human preference labels needed for either.
💬 Have a different checkable task in mind — not guitar tabs, something from your own work? Describe it to your teaching agent and ask what the reward function would look like. That's the one design decision this whole recipe hinges on.
