Lesson 0001 · Fine-Tuning & LoRA

Sticky Notes on a Textbook You Can't Rewrite

Analogy first Picture a massive, printed textbook — 3 billion words, one per tiny fact. You are not allowed to reprint it (too expensive, too slow). But you're allowed to stick thin correction notes onto a few key pages. Readers see the original page plus your note layered on top. That note is LoRA — Low-Rank Adaptation.

A model's "knowledge" lives in giant grids of numbers called weight matrices. Full fine-tuning means changing every number in every grid — for a 3-billion-parameter model, that is 3 billion numbers to track gradients for, which needs a lot of GPU memory. Almost nobody with one GPU can do that.

What LoRA actually adds

For one big frozen matrix W, LoRA trains two small matrices, A and B. Multiplied together, B × A makes a "correction grid" the same size as W — and the model uses W + B×A instead of just W. Only A and B ever get updated.

Illustration — frozen weight + trainable patch

The two thin strips (A and B) are the only pieces glowing — they're the only trainable part. Multiplied together they form a correction the same shape as the giant frozen matrix, and get added on top of it.

Why "low-rank" makes this cheap

A full correction grid the size of W would cost as much to train as W itself. But A and B are deliberately thin — their shared inner dimension, rank r, is tiny (64 here) compared to the matrix's real size. Thin matrices means far fewer numbers to train, at the cost of a slightly less expressive correction. Higher r = more capacity, more VRAM, more time.

Where this lives in your notebook Task 3, cell defining FastLanguageModel.get_peft_model(...): 
r = lora_rank,           # 64 — the "thinness" of A and B
target_modules = [
    "q_proj", "k_proj", "v_proj", "o_proj",     # attention
    "gate_proj", "up_proj", "down_proj",         # feed-forward
],
lora_alpha = lora_rank,  # scales the correction; alpha = r is a stable default
Those seven names are which weight matrices get a sticky note. Lesson 0002 explains what attention and feed-forward layers actually are.

One more choice: 16-bit vs. 4-bit (QLoRA)

Quantization stores each number using fewer bits — like rounding "3.14159265" down to "3.14" to save space. QLoRA combines that trick with LoRA to fit huge models into tiny GPUs. This notebook deliberately skips it and trains in full 16-bit, because GRPO's bottleneck isn't memory — it's generation speed (remember, it generates 8 completions per question, every step), and 16-bit weights generate fastest.

Analogy — why fewer bits can be slower A 4-bit weight is like a zipped file: smaller to store, but your computer has to unzip it before it can actually use it. A 16-bit weight is already unzipped — bigger, but ready to go. GPUs can only do their math (matrix multiplication) in 16-bit-ish formats, so a 4-bit weight has to be decompressed back to 16-bit right before every single calculation. That's a tiny tax — but GRPO generates 8 completions per question, over 175+ steps, so that tiny tax gets paid an enormous number of times.

Illustration — the hidden decompression step

Same destination (GPU math), but the 4-bit path has an extra stop every single time. One decompression is nothing; paying it thousands of times during GRPO's constant sampling is what makes it slower.

16-bit LoRA (this notebook)

More memory used, but no decompression tax — fastest when generation speed is the bottleneck, exactly GRPO's situation.

QLoRA (4-bit)

Less memory used, but pays a decompression tax on every calculation — worth it only when GPU memory itself is the hard limit (e.g. squeezing a big model onto an 8 GB card).
