Lesson 0006 · Training & Results

Watching Reward Climb, Then Swapping Personalities

Every earlier lesson explained one moving piece. This lesson is Tasks 6–9: configure it, hit train, and see what actually changes.

A few configuration knobs, in plain terms

Analogy first learning_rate is how big a step you take with each correction — too big and you overshoot, too small and you barely move. warmup_ratio is easing a car off a stop instead of flooring the gas — a few gentle steps first, so the optimizer's early statistics aren't built on wild swings. lr_scheduler_type = "cosine" is easing off the gas near the end too — a smooth curve down to a gentle stop, rather than slamming the brakes.

One rule is stricter than a suggestion — it's a hard requirement TRL enforces:

The batch-geometry rule per_device_train_batch_size × gradient_accumulation_steps must be evenly divisible by num_generations (the group size, 8). Think of it like splitting a class into study groups of exactly 8 — the total headcount gathered before an update must tile into whole groups, with nobody left over. That's why this notebook pairs batch_size = 1 with gradient_accumulation_steps = 8.

Loss goes down. Reward goes... up.

Every other fine-tuning method you've likely heard of watches a loss number fall. GRPO flips that: there is no "correct" text to compare against, so instead you watch reward — the sum from Lesson 0005 — climb.

Illustration — two different things to watch

Supervised fine-tuning: loss ↓

Steadily, predictably falls as the model copies examples more closely.

GRPO: reward ↑ (eventually)

Flat and noisy for a long while (~100–150 steps here), then climbs once the model starts actually solving problems.

Same x-axis, opposite y-axis story. If your reward graph looks flat for a long time, that isn't broken — it's the normal shape of this kind of training.

Where this lives in your notebook Task 7's markdown cell describes this exact shape: "reward hovers near ~0 and then suddenly starts climbing... expect little movement before step ~100–150." The DeepSeek-R1 paper calls this the model's "Aha moment" — the point where it starts, unprompted, re-checking its own reasoning mid-answer.

Same engine, two personalities

Task 8's clever detail: LoRA never touches the frozen base weights, so the exact same running vLLM engine can generate from the untrained base model or the trained one — just by swapping which adapter rides along.

Illustration — swapping adapters on one frozen engine

Left output: the base model, unstructured. Right output: the exact same engine, same frozen weights — just with the trained LoRA adapter attached — producing the structured reasoning it was trained to.

model.save_lora("grpo_saved_lora") in Task 9 writes only the small A/B matrices from Lesson 0001 — a few hundred megabytes at rank 64, instead of the several gigabytes a full model checkpoint would need. Loading it back with model.load_lora(...) hands you exactly the lora_request object the diagram above swaps in.
