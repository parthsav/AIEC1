# Teaching Notes

## User preferences
- Says "I am new to AI engineering and don't understand anything" — in context this means new to *training/fine-tuning* specifically. Sessions 1–14 covered RAG, agents, evaluation, MCP (all using pretrained models via API), so vocabulary like "prompt," "LLM," "token" can be assumed; vocabulary like "gradient," "policy," "reward," "LoRA rank" cannot.
- Explicitly asked for simpler examples and illustrations/animations over text — same standard as the MCP workspace (Session 8): every lesson needs an analogy first, then a visual, then a grounded code example.
- No stated preference yet on quizzes vs. step-throughs — default to step-through diagrams for processes (the GRPO loop) and side-by-side comparisons for contrasts (LoRA vs full fine-tune, GRPO vs PPO, SFT vs RL).

## Teaching approach
- Teaching order: big picture first (whole pipeline as one animated diagram) → fine-tuning & LoRA → transformer anatomy (needed for Question #2) → RL basics (reward/policy vs SFT) → GRPO algorithm in depth → reward function design & GSM8K → training loop, hyperparameters, and before/after results.
- Ground every lesson in the actual notebook: `01_Reasoning_Fine_Tuning_Unsloth_GRPO.ipynb`, cell IDs and line numbers referenced directly.
- The notebook has 4 in-line questions (Q1: double quantization / 16-bit vs QLoRA, Q2: label the architecture diagram, Q3: what LoRA is doing, Q4: warmup_ratio/learning_rate/lr_scheduler_type). Lessons should build directly toward being able to answer these in the user's own words — don't just answer them for him.
- No GPU assumed available during teaching sessions — never require literally running `trainer.train()` to understand a lesson; use the notebook's own printed outputs/described behavior (reward curve description, `print(model)` dump) as the grounding data instead of live execution.
