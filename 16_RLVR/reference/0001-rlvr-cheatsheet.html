RLVR (Verifiable Rewards) Cheat Sheet

The compressed version of Lessons 0000–0006. Use this mid-notebook when you need a fast reminder, not a first explanation — for that, go back to the lessons.

The loop, in one line

prompt → sample N completions → verify each against a deterministic checker
       → assign rewards → keep verified-correct (unflagged) as preference data
       → policy update (DPO or GRPO) → repeat

Glossary

TermCompressed definition
VerifierA deterministic program that checks correctness — exact match, unit test, schema validation. No training, no judgment call.
Verifiable rewardA reward computed by a verifier rather than a human or a learned reward model. RLVR = RL where every reward comes from one of these.
Learned reward modelRLHF's approach: a network trained to imitate human preference rankings. Approximate, itself gameable — the thing RLVR replaces.
PolicyThe model being sampled from — same meaning as Session 15. Here: a small API model on purpose, so it's sometimes wrong.
Ground truthThe known-correct answer a verifier checks a completion against.
GroupN completions sampled for the same prompt. Same structure GRPO averaged over in Session 15; also the source of correct/incorrect contrast for preference pairs.
Reward hackingA policy exploiting a verifier's blind spots to score well without actually solving the task. See Goodhart's law.
Goodhart's law"When a measure becomes a target, it ceases to be a good measure." Training against a verifier makes the verifier the objective.
Audit trailAn append-only log (verifier.jsonl) of every verifier decision — the record that answers "was this trained on honest rewards?"
Preference pairA {prompt, chosen, rejected} record built from a group's winner and loser. Feeds DPO-style trainers.
SandboxAn isolated, disposable execution environment (Firecracker microVM, gVisor, container) for running untrusted code — the real production version of Task 6's bare subprocess.

RLHF vs. RLVR

RLHFRLVR
Reward sourceA learned reward model, trained on human preference rankingsA deterministic verifier — exact match, unit tests, schema check
Cost per rewardA forward pass through a trained networkRunning a check — usually cheaper, always reproducible
Works when..."Correct" is a matter of taste (persuasiveness, tone, helpfulness)"Correct" is checkable by a program (math, code, structured data)

Math verifier vs. code verifier

Math (Task 3)Code (Task 6)
Reward shapeBinary: +1.0 correct / −0.1 incorrect (asymmetric)Fractional: tests passed ÷ tests total, in [0.0, 1.0]
Check mechanismRegex-extracted \boxed{} vs. ground truth, numerically normalizedExecute in a subprocess, compare stdout to expected
Main riskBrittle extraction punishes correct reasoning; guessing/leakage hacksUntrusted code execution — a security boundary, not just a check

Why the reward is asymmetric (+1.0 / −0.1)

Early in training most attempts fail. A harsh symmetric penalty (−1.0) makes "genuine attempt, wrong" and "no real attempt at all" score identically — nothing separates trying from giving up. A small penalty keeps that distinction alive in the signal.

Building a preference pair (Task 7)

winners = verified-correct samples NOT flagged as hack-suspect
losers  = verified-incorrect samples
pairs   = every (winner, loser) combination within the same group

Hack-suspect samples are excluded from winners — using one as "chosen" would teach the next policy iteration to hack more.

What's different in production

Sandboxed execution (not a bare subprocess) · async/batched sampling at scale, not sequential API calls · verifier hardening (symbolic math checkers, hidden held-out test cases) · governance (versioned audit logs, drift dashboards) · the loop repeats against the updated policy each iteration — this notebook is one lap of that flywheel.
