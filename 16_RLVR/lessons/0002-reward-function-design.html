Lesson 0002 · Reward Function Design

Grading on a Curve That Doesn't Punish You Into Silence

Analogy first Some standardized tests use "negative marking": +1 for a right answer, and a small deduction like −0.25 for a wrong one, with blank answers scoring 0. The deduction is small on purpose — big enough to discourage wild guessing, but small enough that a student who's genuinely trying still comes out ahead of one who leaves everything blank. This notebook's reward function makes the exact same design choice.

The reward function turns "verified" into a number

Lesson 0001 built the referee's rulebook — the extractor and the ground-truth comparison. This lesson is about the score the referee hands back once it's made a call.

Code — Task 3: the math reward function

class MathRewardFunction:
    """Verifiable reward for math problems: exact answer match against ground truth."""

    correct_reward = 1.0
    incorrect_penalty = -0.1

    def compute(self, response: str, ground_truth: str) -> float:
        prediction = extract_number(response)
        if self._normalize(prediction) == self._normalize(ground_truth):
            return self.correct_reward
        return self.incorrect_penalty

    @staticmethod
    def _normalize(value: str):
        """Compare numerically when possible, so '80' == '80.0'."""
        try:
            return float(value)
        except ValueError:
            return value.strip()
Python patterns you'll see here correct_reward = 1.0 sitting directly inside the class (not inside a method) is a class attribute — every instance of MathRewardFunction shares the same value unless overridden. @staticmethod marks a method that doesn't need self — it's just a plain function that happens to live inside the class for organization. try: ... except ValueError: attempts float(value) and, if the string isn't a valid number (like "" when nothing was extracted), falls back to comparing the raw text instead of crashing.

Trace three real calls

These are the exact three assert lines from the notebook — each one is a mini worked example.

Call 1reward_fn.compute(r"The speed is \boxed{80}", "80.0") → extracts "80", normalizes both to the float 80.0, they match → 1.0
Call 2reward_fn.compute(r"The speed is \boxed{81}", "80") → extracts "81", 81.0 != 80.0 → −0.1
Call 3reward_fn.compute("I cannot solve this.", "80") → no box, no fallback number found → extracts "" → "" != 80.0 → −0.1

Notice Call 1: without _normalize, the strings "80" and "80.0" would not be equal, and a genuinely correct answer would get punished purely for formatting. A brittle verifier corrupts the signal it's supposed to protect.

Why not −1.0? The asymmetry is load-bearing

Go back to the negative-marking analogy. Imagine the deduction for a wrong answer were as large as the reward for a right one (−1.0 instead of −0.1). Early in training the policy is wrong most of the time — that's normal, it hasn't learned anything yet. Under a harsh −1.0 penalty, "gave a real, careful, wrong answer" and "produced total nonsense" score exactly the same. Under the gentle −0.1 penalty, a genuine attempt that happens to be wrong lands close to zero — nowhere near as punishing as it could be.

Question #1 — verifiable vs. learned reward, one example each

Lesson 0001 already gave you the core contrast: a verifiable reward comes from a deterministic program, a learned reward model comes from a network trained to imitate human judgment. The notebook's Question #1 asks you to go one step further: name one task where a verifiable reward genuinely exists, and one where it fundamentally can't.

Verifiable reward exists

Anything with a checkable ground truth: this notebook's math problems, code judged by unit tests (Lesson 0005), SQL queries checked against a reference database, JSON checked against a schema.

Fundamentally can't be verified

Anything where "correct" is a matter of taste with no ground truth to check against: is this poem moving? Is this marketing copy persuasive? Is this joke funny? No program can settle it — only human (or human-trained) judgment can, which is exactly why RLHF's learned reward model exists for these cases.
