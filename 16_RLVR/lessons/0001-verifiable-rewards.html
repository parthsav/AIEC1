Lesson 0001 · Verifiable Rewards

A Referee With No Opinions

Analogy first Think about two kinds of referee. A soccer goal has goal-line technology: a sensor either detects the ball fully crossed the line, or it didn't. No opinion, no debate, same answer every time. A gymnastics judge is the opposite: they watch a routine and score it based on trained taste — two judges can watch the same routine and score it differently. RLVR only works with the first kind of referee.

A reward is verifiable when a program — not a person, not another trained model — can check it and get the same answer every time. "Is 156 the right answer to 12×13?" is goal-line technology: a calculator settles it. "Is this poem beautiful?" is gymnastics judging: it needs taste, and taste has to be learned from human examples (that's what RLHF's learned reward model is — a model trained to imitate a judge's taste).

RLHF: a learned reward model

Humans rank pairs of outputs ("this one's better"). A separate neural network is trained to predict those rankings. It's a judge — approximate, and itself capable of being fooled.

RLVR: a verifier

A deterministic program — regex match, unit test, calculator — checks the output directly. No training, no judgment call, no drift. Cheap, objective, reproducible.

Two pieces make a verifier possible: the policy, and the ground truth

1. The policy is chosen to sometimes fail — on purpose

The notebook uses gpt-4.1-nano at temperature 1.0 — a small, somewhat unreliable model, not the best one available. That's deliberate. If the policy got every problem right, every sample would look identical to the verifier: all correct, no contrast. A referee only tells you something useful when there's a real chance of a foul.

2. Ground truth + the \boxed{} convention makes checking mechanical

Each problem carries its correct answer as a plain string, and the policy is instructed to wrap its final answer in \boxed{...} — the exact convention GSM8K-style training uses, which you already saw feeding Session 15's reward function. That turns "did the model get it right?" from a judgment call into a regex search.

Code — Task 2: the problem and the extractor

@dataclass
class Problem:
    question: str
    answer: str  # ground truth

def extract_number(text: str) -> str:
    r"""Pull the final answer out of a completion: \boxed{...} first, last number as fallback."""
    boxed = re.search(r"\\boxed\{([^}]+)\}", text)
    if boxed:
        return boxed.group(1).strip()
    numbers = re.findall(r"-?\d+\.?\d*", text)
    return numbers[-1] if numbers else ""
Python patterns you'll see here @dataclass auto-generates a simple container class from the fields you list — Problem("What is 12*13?", "156") just works, no boilerplate __init__. re.search(pattern, text) finds the first match of a regex pattern and returns it (or None); re.findall(...) returns all matches as a list. The r"..." prefix is a "raw string" — it tells Python not to treat \b as a special escape code, so the regex engine sees the literal backslash it needs to match \boxed.

3. extracted = boxed.group(1).strip()extracted = "156"
4. Compare to ground truth"156" == "156" → verified correct. This is now a checkable fact, not an opinion.

If the model had instead written just "the speed is 80 km/h" with no box (the notebook's second test case), re.search would find nothing, and the function falls back to re.findall — grabbing the last plain number in the text as a best guess.
