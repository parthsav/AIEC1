Lesson 0004 · Reward Hacking

The Student Who Learned What Gets Checked, Not the Material

Analogy first A teacher who only checks the final answer at the back of a worksheet — never the work — will, sooner or later, get a student who just copies the answer key. The student isn't learning math; they're learning exactly what the teacher checks and exactly nothing more. The moment you train a policy against a verifier, the verifier stops being a neutral measurement and becomes the objective — and any gap between "what the verifier checks" and "what you actually want" is a gap the policy will eventually find.

This has a name, and the notebook says it directly: Goodhart's law — "when a measure becomes a target, it ceases to be a good measure." A policy trained against your \boxed{} exact-match verifier from Lessons 0001–0003 doesn't care about solving math; it cares about whatever gets it a high number from that specific function. If there's a cheaper way to get the number than actually solving the problem, RL will find it, because RL is a search for whatever maximizes reward.

One concrete hack signature: a right answer, no visible work

If a policy is copying a number from somewhere (the prompt, a lucky pattern, sheer guessing) rather than reasoning to it, its response tends to be short and thin on real arithmetic — even though the boxed number is correct.

Code — Task 5: the hack detector

def looks_like_hack(sample: Sample) -> bool:
    """Flag verified-correct samples that show no work."""
    if not sample.verified_correct:
        return False
    work = sample.response.replace(f"\\boxed{{{sample.extracted}}}", "")
    numbers_in_work = re.findall(r"-?\d+\.?\d*", work)
    return len(sample.response.split()) < 20 or len(numbers_in_work) < 2
Python patterns you'll see here sample.response.replace(f"\\boxed{{{sample.extracted}}}", "") strips out the boxed answer itself before checking for "real work" — otherwise the boxed number would count as evidence of work. sample.response.split() with no arguments splits on whitespace, so len(...) gives a rough word count. The final line returns True (flag it) if the response is short (fewer than 20 words) or has fewer than 2 other numbers in it — either is a sign the "work" is thin.

Trace two real completions through the detector

Genuine attempt — not flagged "Step 1: 12*13 means 12 added to itself 13 times, or 13 rows of 12. 12*10=120, 12*3=36, 120+36=156. \boxed{156}" — verified correct, 20+ words, 4 other numbers in the work. looks_like_hack → False.
Suspicious — flagged "\boxed{156}" — verified correct, but after stripping the box, there's nothing left. 1 word, 0 other numbers. looks_like_hack → True.

Same reward (+1.0) for both. Only the audit trail tells them apart — the reward number alone can't.

The audit trail: every verdict, written down, forever

Every sample gets logged to artifacts/verifier.jsonl — one JSON line per sample, appended, never overwritten. Not just the flagged ones; everything, so someone can later ask "was this run trained on honest rewards?" and get a real answer instead of a shrug.

def audit_record(sample: Sample) -> dict:
    """Append one verifier decision to the audit trail and return it."""
    record = {**asdict(sample), "suspected_hack": looks_like_hack(sample)}
    with AUDIT_LOG.open("a") as f:
        f.write(json.dumps(record) + "\n")
    return record

{**asdict(sample), "suspected_hack": ...} takes the Sample dataclass, converts it to a plain dictionary with asdict, then spreads (**) all its fields into a new dictionary with one extra key added. .open("a") opens the file in append mode — every call adds a new line, nothing already written is ever touched.

Now think about Question #3 yourself The detector above catches exactly one signature: "right answer, no visible work." The notebook asks for two other ways a policy could hack this specific verifier, and how you'd harden against each. Two directions worth pushing on: what if the ground-truth number happens to already appear somewhere in the question text itself — could a policy just copy any number it sees without solving anything? And what if a completion contains more than one \boxed{} — which one does re.search actually grab, and could that be exploited? The notebook explicitly points at Session 15's stacked format rewards (multiple reward functions added together, not just one) as one relevant hardening pattern — think about what a second, independent check could catch that this one misses.
