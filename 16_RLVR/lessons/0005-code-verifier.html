Lesson 0005 · The Code Verifier

A Referee That Runs the Program Instead of Reading It

Analogy first A driving test isn't pass/fail on one thing — it's a checklist: parallel parking, stop signs, merging, signaling. You don't get a single "correct/incorrect"; you get a fraction of checkpoints passed, and that fraction is the score. Code verification works the same way: instead of one exact-match check like math had, a program runs against several test cases, and the reward is the fraction that pass.

Math and code are the two workhorse domains of RLVR, and they differ in one important way: math's verifier is binary (exact match or not), while code's verifier is fractional — a number in [0.0, 1.0].

Code — Task 6: the verifier

class CodeVerifier:
    """Score generated code by the fraction of test cases it passes."""

    timeout_seconds = 5

    def verify(self, code: str, test_cases: list[dict]) -> float:
        passed = 0
        for tc in test_cases:
            try:
                output = self._run(code, tc.get("input", ""))
                if output.strip() == str(tc["expected"]).strip():
                    passed += 1
            except Exception:
                pass  # crash, timeout, or non-zero exit -> no credit for this case
        return passed / len(test_cases) if test_cases else 0.0

    def _run(self, code: str, input_data: str = "") -> str:
        result = subprocess.run(
            [sys.executable, "-c", code],
            input=input_data, capture_output=True, text=True,
            timeout=self.timeout_seconds,
        )
        if result.returncode != 0:
            raise RuntimeError(result.stderr)
        return result.stdout
Python patterns you'll see here subprocess.run([sys.executable, "-c", code], ...) launches a brand-new Python process and hands it your candidate code as a -c (run-this-string) argument — it's a completely separate program, not a function call inside your notebook. input=input_data feeds text to that process's standard input, the same as if a person typed it. timeout=self.timeout_seconds kills the process if it hasn't finished in 5 seconds. except Exception: pass means any failure — a crash, a timeout, non-zero exit — silently earns zero credit for that one test case, rather than crashing the whole loop.

Worked example — three candidates, one task

Task: write a program that reads n and prints the sum of squares from 1 to n. Test cases: n=1→1, n=3→14, n=10→385.

Correct candidate n = int(input()); print(sum(i * i for i in range(1, n + 1))) — passes all 3 → reward 1.0
Buggy candidate n = int(input()); print(sum(range(1, n + 1))) — sums i, not i². Fails all 3 → reward 0.0
A partial-credit candidate (imagine one) A program with an off-by-one bug might pass n=1 and n=3 but fail n=10 — reward 0.67 (2 of 3). This is the fractional signal math's binary match can never produce: "almost right" and "completely wrong" get different scores.
Read the warning in your notebook literally "We are executing model-generated code on your machine." subprocess.run is a real, separate operating-system process with real access to your machine — it is not a safe little sandbox by default. The 5-second timeout stops a program that hangs forever, and nothing else. It does nothing to stop a program that reads your files, opens a network connection, or does damage in well under 5 seconds.
Now think about Question #4 yourself Two parts. First: fractional rewards give richer signal ("almost right" vs. "totally wrong" are now distinguishable) — but what's the risk of that richness? Think about whether a policy could learn to target a comfortable middle score instead of pushing for full credit. Second, concretely: our verifier runs candidates directly on the host with only a timeout as protection. What could a policy-generated program actually do in under 5 seconds, and which of those things does the timeout not cover at all?
Where production differs Your notebook says it directly: production verifiers run untrusted code in isolated, disposable environments — ephemeral microVMs like Vercel Sandbox (Firecracker-based), or self-hosted gVisor / locked-down containers — never a bare subprocess on the same machine that's running your training loop. The verifier defines the reward, which makes its execution environment a security boundary, not just a technical detail.
