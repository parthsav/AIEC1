How a question finds its answer

Before we teach a computer to find pictures, let's nail how it finds text. Everything in your notebook stands on this one idea.

⏱ about 15 minutes · uses the real ACME files from data/text/ · cheat sheet for later

The problem RAG solves

A model like GPT-4o has read the public internet. It has never read your files. Ask it about ACME Robotics and it can only guess.

Analogy RAG turns a closed-book exam into an open-book exam. The model doesn't memorize your documents — it gets to look up the right page just before it answers.

RAG stands for Retrieval-Augmented Generation: retrieve the right snippets, then generate an answer from them. The hard part is the lookup. How does a computer know which page is "the right page"?

The magic trick: a map of meaning

Analogy Imagine a GPS for sentences. Every sentence gets map coordinates — and sentences that mean similar things get coordinates that are near each other. To answer a question, you drop the question onto the map and grab whatever is standing closest.

That coordinate list is called an embedding. It's the only new word you need right now.

Interactive · The meaning map of your six ACME documents
Click a question to drop it onto the map. Watch where it lands — and which document lights up as its nearest neighbor.
Key idea An embedding is just a list of numbers — 1,536 of them for text-embedding-3-small, the model in your notebook. This map squashes those 1,536 dimensions down to 2 so we can see them. Nearby lists = similar meaning. That is the entire trick underneath all of RAG.

Look at question 2 again: “How much goes to compute vs storage?” shares almost no words with doc_finance_costs.md — no “cloud”, no “cost”. A keyword search would miss it. The meaning map still puts them side by side, because they're about the same thing.

The whole pipeline, one document at a time

Text RAG is five steps. Step through them below and watch one real ACME document — doc_board_notes.md — travel the entire journey.

Step-through · One document's journey from file to answer
① CHUNK — cut documents into bite-sized pieces
📄 data/text/doc_board_notes.md
Revenue was strongest in the final quarter, driven by a large public-sector deal. Churn improved materially after the onboarding revamp, but spiked in March due to a billing bug that double-charged a cohort of customers…

Like copying a book onto index cards — one card, one idea. Your ACME documents are already tiny, so the notebook keeps each file whole: one file = one chunk (Cell 3.2 loads them).

The chunk goes in; 1,536 numbers come out — its coordinates on the meaning map. Same text in, same numbers out, every time.

③ STORE — file the coordinates in a vector database
🗄 Qdrant collection “strategy_a” (running in memory)
idvectororiginal text
doc_board_notes.md[0.021, −0.043, …]“Revenue was strongest…”

A vector database is a filing cabinet sorted by meaning instead of alphabet. Yours is called Qdrant; the notebook runs it inside the notebook process — no server needed.

④ RETRIEVE — drop the question on the map, grab the 3 nearest
❓ “What caused the March churn spike?” → embedded with the same model → its own coordinates
Nearest neighbors (k = 3):
1. doc_board_notes.md  ← “billing bug… double-charged” ✓
2. doc_product_roadmap.md
3. doc_finance_costs.md

This is exactly what the meaning map above animated. k=3 just means “bring back the 3 closest chunks”.

⑤ ANSWER — paste the found chunks into the model's prompt
Question: What caused the March churn spike?
--- CONTEXT ---
[doc_board_notes.md]: …spiked in March due to a billing bug…
[doc_product_roadmap.md]: …onboarding revamp shipped…
--- END CONTEXT --- Answer with citations.
↓
💬 “The March churn spike was caused by a billing bug that double-charged a cohort of customers [doc_board_notes.md].”

The open-book exam, delivered: the model answers from the pages we handed it and cites which page. That's “generation”, grounded.

The five steps of text RAG: chunk → embed → store → retrieve → answer. Steps ①–③ happen once, up front (“ingestion”). Steps ④–⑤ happen every time you ask (“query time”).

Here's exactly where this lives in your notebook

Open multimodal_rag.ipynb, Section 5, “Strategy A” (Cell 5.1). All five steps hide inside seven lines:

Code spotlight · multimodal_rag.ipynb — Section 5, Cell 5.1
# steps ② EMBED and ③ STORE happen inside this one call:
store_A = QdrantVectorStore.from_documents(docs_A, text_embedder,
              location=":memory:", collection_name="strategy_a")

# step ④ RETRIEVE — embeds your query, returns the k nearest chunks:
def retrieve_A(query, k=3):
    return store_A.similarity_search(query, k=k)
Step ① (chunking) is Cell 3.2, which loads each file as one chunk. Step ⑤ (answering) is Section 7's answer() function — it pastes retrieved chunks into the prompt exactly like the step-through showed.

The number $27M appears in no text file anywhere in the corpus. It exists only as pixels inside this picture.

Everything you just learned runs on text. An embedding model reads words — hand it a PNG and it's blind. To the pipeline above, this chart is invisible: it can never be found, and its $27M can never be cited.
